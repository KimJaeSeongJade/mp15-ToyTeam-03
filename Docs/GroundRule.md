# TEAM 3 (탕수육 찍먹파) Ground Rule

> ## 기본 원칙
> - 다른 팀원이 작업 중인 Scene을 사전 협의 없이 수정하지 않는다. 
> - 공용 Prefab을 사전 협의 없이 수정하지 않는다. 
> - `.meta` 파일을 임의로 삭제하거나 수정하지 않는다. 
> - 하루 최소 1회 이상 PR을 올린다.
> - 매일 오후 5시 데일리 체크인을 작성한다.
> - 문제가 생기면 혼자 오래 끌지 않고 공유한다.
> - 일정 변동이 생기면 팀장, PM에게 즉시 알린다.

---

# 1. 소통 규칙

## 1-1. 기본 소통

- 팀 소통은 Slack을 기본으로 사용한다.
- `소통 채널`과 `GitHub 알림 채널`을 구분하여 사용한다.
- 일정 변경이나 작업 지연 가능성이 있는 경우 미리 Slack으로 공유한다.
- 일정과 관련된 중요 내용은 팀장 또는 PM을 멘션(`@`)하여 전달한다.
- 질문에 대한 답변은 해당 메시지의 댓글을 사용한다.
- 답변이 필요없는 메시지의 경우 확인 후에 초록 체크 이모지 반응을 남겨 확인 여부를 알린다.

---

## 1-2. 작업이 막혔을 때

작업이 막힌 경우 아래 순서로 진행한다.

1. 에러 메시지와 코드 위치를 확인한다.
2. 공식 문서 또는 검색을 통해 해결 방법을 확인한다.
3. 해결되지 않으면 `Slack`에 현재 상황을 공유하여 팀원과 토의한다.
4. 팀 내에서 해결되지 않으면 팀장 또는 PM과 상의한다.
5. 4번에서 해결이 안되는 경우 강사님께 질문한다.

질문을 올릴 때는 아래 내용을  작성한다.

- 어떤 작업을 진행하고 있었는지
- 어디에서 문제가 발생했는지
- 에러 메시지
- 에러가 발생한 코드 또는 파일
- 원래 기대한 동작
- 직접 시도해 본 해결 방법

---

# 2. 작업 및 GitHub 규칙

## 2-1. 작업 시작

모든 작업은 `GitHub Issue`를 통하여 브랜치를 생성하여 진행한다.
Issue로 해당 작업 선언 후에 해당 Issue로 브랜치를 생성하여
본인 업무를 진행한다. 모든 브랜치는 `main-develop` 브랜치를 기준으로 생성한다.
> 직접 `main` 또는 `develop` 브랜치에서 기능 개발을 진행하지 않는다.

자세한 내용은 컨벤션 문서의 Github 협업 사용 가이드를 참고한다.

---

## 2-2. 브랜치

브랜치는 다음 형식으로 작성한다.

`커밋태그/작업자이니셜/작업설명`

예시:

`feat/yr1103/monster-movement`

`fix/yr1103/tower-targeting`

`docs/yr1103/ground-rule`

작업 단위는 가능한 한 작게 나눈다.

예:

몬스터 전체 기능을 하나의 브랜치에서 모두 구현하기보다

- monster-movement
- monster-attack
- monster-health

처럼 기능 단위로 나누어 진행한다.

---

# 3. PR 및 Merge 규칙

## 3-1. PR 생성

기능 구현 또는 해당 작업 단위가 끝나면 PR을 생성한다.
자세한 내용과 작성 양식은 컨벤션을 통해 확인한다.
PR에는 다음 내용을 작성한다.

- 무엇을 구현했는지
- 어떤 파일 또는 기능과 연관되어 있는지
- 구현한 이유
- 직접 확인한 내용
- 다른 작업자가 확인해야 할 사항
- 필요한 경우 실행 화면 또는 이미지

---

## 3-2. 코드 리뷰

PR이 올라오면 본인 기능과 관련된 작업자들이 내용을 확인한다.

특히 다음 사항을 확인한다.

- 본인 작업과 충돌하는 부분이 있는지
- 공용 기능이 변경되었는지
- Scene 또는 Prefab 변경이 포함되어 있는지
- 이해되지 않는 코드가 있는지
- 실행 시 문제가 발생하지 않는지

일반적인 의견은 `Comment`로 작성한다.

반드시 수정되어야 하는 문제가 있는 경우 `Request changes`를 사용한다.

---

## 3-3. Merge 확정

작업 완료 후 Merge 진행 전 아래 인원에게 알려 최종 확인한다.

1. 해당 기능과 직접 연관된 작업자
2. 팀장
3. 팀장이 확인하기 어려운 경우 PM

최종 확인이 끝난 뒤 `Merge`를 진행하기 전
> ## Base Branch가 `main-develop`인지 확인한다.
> ### `main`으로 `Merge`하지 않는다.

Merge를 진행하게되면 :

- 연결된 Issue가 `Close` 처리된다.
- Kanban Board의 상태를 `Done`으로 변경한다.
- 해당 작업 브랜치는 더 이상 사용하지 않는다.

---

# 4. 회의 규칙

## 오전 회의 — 전날 작업 정리

회의는 매일 2교시 시작 시간에 진행한다.

**시간: 10:00 ~ 10:30**

1교시에는 각자 전날 작업 내용을 정리하고 회의를 준비한다.

회의에서 공유할 내용:

- 전날 진행한 작업
- 막혔거나 해결하지 못한 작업
- 오늘 진행할 작업
- 다른 팀원과 협의가 필요한 내용

회의 중 필요한 부분을 토의하고 작업 내용을 보완한 뒤 개발을 진행한다.

---

## 오후 회의 — 데일리 체크인 전 회고

데일리 체크인 작성 전에 간단한 회의를 진행한다.

**예상 시간: 10 ~ 30분**

공유할 내용:

- 오늘 진행한 작업
- 현재 작업 진행 상태
- 팀원들이 알아야 할 변경 사항
- 다음 작업에 영향을 주는 내용

오후 회의 이후 오후 5시 데일리 체크인을 작성한다.

---

## 주말

주말에 팀 공통 업무가 예정되어 있는 경우 팀원들과 시간을 조정하여 진행한다.

개인 작업만 진행하는 경우 별도 회의를 강제하지 않으며,
필요한 내용은 Slack을 통해 공유한다.
